# PMMP C/C++ hybrid engine 최고성능 계획

Updated: 2026-06-10 KST

## 목표

PMMP 플러그인 호환을 우선 유지하면서, Dragonfly식 비동기/transaction 설계와 Folia식 region ownership 원칙을 참고해 PMMP의 무거운 hot path를 C/C++ native engine lane으로 이동한다.

최종 목표는 다음이다.

- 기존 PMMP 플러그인은 기본적으로 PHP main compatibility thread에서 그대로 동작한다.
- C/C++은 live PMMP 객체를 직접 만지지 않고, immutable snapshot과 binary buffer만 처리한다.
- 네트워크, packet fanout, chunk snapshot serialization, visibility, compression, 역직렬화/직렬화, dirty-set 계산을 worker/native로 뺀다.
- 400명 같은 구역 밀집 상황에서는 region 분할보다 hotspot fanout worker가 우선이다.
- 넓게 퍼진 야생 상황에서는 region actor를 제한적으로 병행한다.

## 조사 근거

### PMMP threading 제약

PMMP 공식 threading 문서는 PHP의 복잡한 자료구조가 thread-safe하지 않고, thread 간 전달 시 복사 비용이 크다고 설명한다. 또한 PMMP가 현재 thread를 쓰는 영역은 월드 생성, lighting, network compression, 일부 network system, cURL 정도라고 밝힌다.

출처: https://doc.pmmp.io/en/rtfd/developers/threading-in-php-wtf.html

우리 설계 결론:

- PHP object, array, closure, plugin instance를 worker로 보내지 않는다.
- worker 입력은 scalar ID, packed binary, immutable snapshot, version number로 제한한다.
- worker 결과는 plain result로 반환하고, PHP main이 PMMP 순서대로 최종 적용한다.

### Dragonfly 참고점

Dragonfly는 Go 기반 Bedrock 서버이고 README에서 heavily asynchronous server software라고 설명한다. Dragonfly world API는 v0.10.0 이후 `World.Exec()`와 `world.Tx` transaction 모델을 사용한다. `Tx`는 world에 대한 synchronised transaction이며, 여러 goroutine에서 동시에 쓰면 안 되는 것으로 문서화되어 있다.

출처:

- https://github.com/df-mc/dragonfly
- https://pkg.go.dev/github.com/df-mc/dragonfly/server/world

우리 설계 결론:

- PMMP도 live mutation은 transaction/commit 경계로 모은다.
- `World`, `Entity`, `Inventory`, `Player` 직접 변경은 compatibility commit phase에서만 한다.
- native worker는 후보 계산만 하고, 최종 적용은 `CommitQueue`가 한다.

### Folia 참고점

Folia는 loaded world chunks를 independent ticking regions로 나눠 병렬 tick한다. regionizer는 각 chunk holder가 하나의 region만 갖는 invariant, merge radius, ticking region이 tick 중 소유 영역을 확장하지 않는 invariant를 둔다. inter-region 작업은 EntityScheduler, RegionizedTaskQueue, global region task queue 같은 queue로 해결한다.

출처:

- https://docs.papermc.io/folia/reference/overview/
- https://docs.papermc.io/folia/reference/region-logic/

우리 설계 결론:

- region actor는 넓게 퍼진 야생/섬/미니게임/월드 분리에만 쓴다.
- 같은 구역 400명 밀집은 하나의 region에 몰리므로 region actor만으로 해결하지 않는다.
- cross-region mutation은 direct call 금지, message/commit queue로만 처리한다.

### Bedrock/RakNet 참고점

Bedrock external server는 RakNet/UDP를 사용하고 기본 IPv4 포트는 19132다. BedrockProtocol은 PHP packet encode/decode 구현이지만 JWT, encryption, compression은 포함하지 않는다고 밝힌다.

출처:

- https://wiki.bedrock.dev/servers/raknet
- https://github.com/pmmp/BedrockProtocol

우리 설계 결론:

- RakNet/UDP edge, compression, packet batch encode/decode, packet replay/fuzzing은 별도 hot path로 본다.
- BedrockProtocol PHP packet object 생성은 호환성 경계로 남기되, binary framing/length/primitive packing은 native로 이동한다.

### gophertunnel 참고점

gophertunnel은 Bedrock Edition software용 Go protocol toolkit이고, 보통 최신 공식 Minecraft 버전 하나를 지원한다고 설명한다.

출처: https://github.com/Sandertv/gophertunnel

우리 설계 결론:

- Dragonfly식 최신 프로토콜 추적 속도는 참고하되, PMMP plugin API 안정성을 버리지 않는다.
- protocol replay fixture를 만들어 PMMP BedrockProtocol, native decoder, optional Go/Rust sidecar 결과를 비교한다.

## 목표 아키텍처

```text
PHP main compatibility/event commit thread
  - PMMP plugin API
  - event order
  - permission/command/final validation
  - authoritative world/entity/inventory mutation
  - final packet scheduling

Native engine layer
  - C ABI stable functions
  - binary serialization/deserialization
  - chunk snapshot encode/decode
  - packet fanout assembly
  - AOI/visibility candidate calculation
  - dirty-set coalescing
  - compression policy and payload transforms

Worker pools
  - packet encode/compress workers
  - chunk snapshot serialization workers
  - movement/visibility/fanout candidate workers
  - plugin storage write-behind workers
  - metric aggregation workers

CommitQueue
  - applies worker result on PHP main thread
  - preserves PMMP event order
  - validates snapshot version
  - drops stale worker results
```

## 핵심 원칙

1. Live PMMP object를 worker/native에 넘기지 않는다.
2. 모든 worker job은 immutable input -> immutable output이어야 한다.
3. world/entity/inventory mutation은 main commit phase에서만 한다.
4. plugin event가 취소 가능한 동작은 worker가 최종 결정하지 않는다.
5. packet payload는 한 번 만들고 여러 recipient에 공유한다.
6. same-area 400명은 `O(players * viewers)` 스캔을 dirty-set/subscription으로 줄인다.
7. region actor는 넓은 분산 상황용이고, hotspot worker는 밀집 상황용이다.
8. 모든 native fast path는 PHP fallback과 byte-equivalence test를 갖는다.

## 설계 단위

### 1. Native Packet Engine

목표:

- packet batch framing을 C/C++에서 처리
- packet length VarInt, packet id, subclient header, batch payload를 직접 write
- duplicate serialization 제거
- recipient별 다른 부분만 patch 가능한 payload template 도입

구현 후보:

- `pmmp_perf_encode_packet_batch_template(array|string $payloads, array $patches): string`
- `pmmp_perf_build_fanout_payload(string $base, array $recipientDeltas): array`
- `pmmp_perf_decode_gamepacket_header_batch(string $batch): array`
- packet replay fixture: PHP BedrockProtocol result와 native result 비교

성공 기준:

- movement-fanout에서 duplicate packet serialization `50%+` 감소
- packet encode p95 `30%+` 감소
- byte-equivalence mismatch `0`

### 2. Native Chunk Snapshot Engine

목표:

- live chunk가 아니라 immutable snapshot을 worker에 전달
- paletted array, biome palette, block entity NBT pointer/serialized blob을 snapshot화
- worker/native에서 full chunk payload 생성
- 동일 chunk를 여러 player가 요청하면 payload 공유

snapshot shape:

```text
ChunkSnapshot
  worldId
  chunkX
  chunkZ
  version
  subchunkCount
  heightMapHash
  biomeHash
  palettedBlockBuffers[]
  blockEntityNbtBlob
  lightBlob optional
```

구현 후보:

- `ChunkSnapshotBuilder` PHP: main thread에서 scalar/binary snapshot 생성
- `NativeChunkSerializer` C/C++: snapshot -> network payload
- `ChunkPayloadCache`: `(worldId, x, z, version, protocolId, compressionPolicy)` key
- `ChunkJobQueue`: stale version drop

성공 기준:

- spawn-chunk-burst p95 chunk ready latency `30%+` 감소
- full chunk serialization worker queue backlog 안정
- stale chunk result drop 정상

### 3. Hotspot Visibility/Fanout Engine

목표:

- 400명 같은 구역에서 viewer scan을 매 tick 전수 조사하지 않는다.
- player movement를 cell grid/interest set으로 coalescing한다.
- worker는 후보 viewer list만 계산하고 main은 plugin/event/permission 최종 검증한다.

data structure:

```text
HotspotGrid
  cellSize = 8 or 16 blocks
  playerId -> cell
  cell -> playerIds bitset
  dirtyPlayers bitset
  dirtyEntities bitset
  subscriptions[playerId] -> visible target bitset
```

구현 후보:

- native bitset intersection/union
- `pmmp_perf_aoi_diff(oldCells, newCells, radius): added/removed`
- per-tick movement packet coalescer
- same-position/no-visible-change skip

성공 기준:

- movement-fanout outbound packet count `20%+` 감소
- per-tick viewer scan count `70%+` 감소
- visibility desync report `0`

### 4. Dirty UI/Scoreboard/Metadata Engine

목표:

- scoreboard/actionbar/bossbar/form text를 매 tick 재전송하지 않는다.
- 값이 바뀐 player/line만 dirty로 표시한다.
- cosmetic update는 gameplay-critical packet 뒤로 밀고 rate-limit한다.

구현 후보:

- `DirtyStateRegistry`
- `ScoreboardDiffBuffer`
- `MetadataDiffBuffer`
- `ActionbarRateLimiter`
- native string hash/diff helper는 필요한 경우만

성공 기준:

- 400명 hotspot UI packet `50%+` 감소
- scoreboard/actionbar tick cost `50%+` 감소

### 5. Async Storage / Plugin I/O Containment

목표:

- PMMP plugin 호환을 유지하되, main tick file/db write를 write-behind queue로 감싼다.
- plugin API를 깨지 않기 위해 wrapper를 optional로 제공한다.

구현 후보:

- `AsyncJsonStore`
- `AsyncYamlStore`
- `BatchedWriteBehindQueue`
- `MainThreadReadCache`
- plugin hotpath auditor와 연동

성공 기준:

- plugin-io scenario에서 p95 tick spike `50%+` 감소
- crash/restart 후 저장 데이터 손실 없음

### 6. Region Actor Experimental Lane

목표:

- Folia invariant를 PMMP에 그대로 이식하지 않고, 안전한 제한 영역부터 실험한다.
- separated wild area, island, minigame arena, separate world 단위에만 적용한다.

region ownership:

```text
RegionActor
  owns region sections
  owns immutable tick-local data
  cannot call PMMP plugin directly
  emits CommitIntent

Main Commit Thread
  validates CommitIntent
  fires plugin events
  applies accepted mutation
```

금지:

- worker/actor에서 `World::setBlock()` 직접 호출
- worker/actor에서 `EntityDamageEvent` 직접 fire
- plugin object 접근
- cross-region direct mutation

성공 기준:

- isolated arena에서 entity/path candidate worker 동작
- cross-region teleport는 queue로만 수행
- PMMP plugin event order regression `0`

## Thread model

| Lane | Thread | Input | Output | PMMP 호환 위험 |
|---|---|---|---|---:|
| packet framing | native/worker | binary packet list | binary batch | Low |
| compression | worker/native | binary batch | compressed binary | Low |
| chunk snapshot serialization | worker/native | immutable snapshot | chunk payload | Low-Medium |
| AOI/visibility | worker/native | player positions, bitsets | candidate target IDs | Medium |
| metadata/UI dirty diff | main+worker | scalar states | packet intents | Medium |
| entity AI/path candidate | worker | entity snapshot | movement/action candidates | Medium-High |
| world/entity/inventory mutation | main | commit intent | applied mutation | High if threaded |
| plugin event | main | event object | plugin result | High if threaded |

## C/C++ 모듈 계획

### Native engine ABI 원칙

PHP extension과 sidecar worker 모두 같은 데이터 계약을 따른다.

```text
EngineJob
  jobType: u16
  protocolId: u32
  worldId: u32
  tick: u64
  snapshotVersion: u64
  flags: u32
  payloadLen: u32
  payload: bytes

EngineResult
  status: u16
  jobType: u16
  snapshotVersion: u64
  metricCostNs: u64
  outputLen: u32
  output: bytes
```

규칙:

- ABI에는 PHP object pointer를 넣지 않는다.
- 모든 integer는 little-endian으로 고정한다.
- payload 내부 VarInt는 Bedrock/RakNet protocol 규칙을 따른다.
- result에는 commit 가능한 `intent` 또는 이미 직렬화된 binary payload만 넣는다.
- result가 stale version이면 PHP main commit thread가 폐기한다.
- native crash가 server process를 죽일 가능성이 큰 작업은 extension이 아니라 sidecar worker로 보낸다.

### `pmmp_perf_ext` v2

역할:

- 현재 PHP extension 유지
- binary primitive와 packet/chunk helper 추가
- PHP fallback 필수

추가 함수 후보:

- `pmmp_perf_bitset_or(string $a, string $b): string`
- `pmmp_perf_bitset_andnot(string $a, string $b): string`
- `pmmp_perf_aoi_grid_diff(string $positions, int $radius): array`
- `pmmp_perf_encode_packet_templates(array $templates, array $patches): array`
- `pmmp_perf_serialize_chunk_snapshot(string $snapshot): string`
- `pmmp_perf_decode_packet_headers(string $batch): array`

### `pmmp_engine_worker` sidecar 후보

역할:

- PHP extension보다 긴 작업을 별도 process/thread pool로 처리
- crash isolation 확보
- IPC는 shared memory or named pipe 후보

적합 작업:

- chunk snapshot bulk serialization
- long AOI recompute
- packet replay/fuzz test
- metric aggregation

비적합 작업:

- plugin callback
- live object mutation
- synchronous command handling

## 직렬화/역직렬화 고속화 계획

### Packet deserialization

현재 병목 후보:

- PHP packet object 생성 비용
- VarInt 반복 decode
- batch 내부 packet header scan
- NBT/string/binary copy

개선:

- native에서 batch header index를 한 번 만든다.
- PHP는 필요한 packet만 lazy materialize한다.
- movement, inventory transaction, chunk request 같은 빈번한 packet은 header-only fast reject를 둔다.
- unknown/custom packet은 기존 BedrockProtocol PHP path로 fallback한다.

구현 후보:

- `PacketBatchIndex`: batch offset, packet id, sender subclient, payload length 배열
- `LazyPacketView`: PHP object 생성 전 binary slice 참조
- `FastPacketGate`: movement/chunk request/login/status처럼 높은 빈도 packet만 native pre-parse

### Packet serialization

현재 병목 후보:

- 같은 packet을 player 수만큼 반복 encode
- packet id/VarInt/batch prefix 반복 write
- recipient별 작은 차이 때문에 전체 payload 재생성

개선:

- `PacketTemplate`을 만들고 recipient delta만 patch한다.
- entity/player metadata는 dirty field만 patch한다.
- broadcast packet은 compressed payload까지 공유 가능한지 분리 측정한다.

구현 후보:

```text
PacketTemplate
  packetId
  staticPrefix
  patchSlots[]
  staticSuffix

PatchSlot
  offset
  type
  maxLen
  recipientValueId
```

성공 기준:

- 같은 entity movement broadcast에서 encode 호출/player 비율 `0.2 이하`
- packet byte-equivalence mismatch `0`
- compression 전 shared payload hit rate `60%+`

### Chunk serialization

현재 병목 후보:

- live chunk 구조 접근
- palette/biome 반복 encode
- 동일 chunk payload 중복 생성
- block entity NBT copy

개선:

- main thread는 snapshot만 만든다.
- native worker는 snapshot binary를 network payload로 만든다.
- `ChunkPayloadCache`는 protocol id, compression policy, chunk version을 key로 한다.
- block entity NBT는 hash와 blob으로 분리해 동일 blob 재사용을 측정한다.

성공 기준:

- 400명 접속/텔레포트 burst에서 chunk payload 중복 생성 `70%+` 감소
- stale chunk result drop 누락 `0`
- chunk corruption fuzz mismatch `0`

## Dragonfly식 메커니즘을 PMMP로 변환하는 방법

Dragonfly의 핵심은 모든 것을 동시에 막 돌리는 것이 아니라, world mutation을 transaction 경계 안에 넣고 나머지를 비동기로 밀어내는 구조다. PMMP에서는 다음처럼 바꾼다.

| Dragonfly 개념 | PMMP 적용 |
|---|---|
| `World.Exec()` transaction | `CommitQueue::flushTick()` |
| `world.Tx` 안에서만 authoritative mutation | PHP main compatibility thread에서만 world/entity/inventory 변경 |
| goroutine worker | C/C++ extension fast path 또는 sidecar worker |
| async network/protocol stack | packet template, batch index, fanout worker |
| library-first protocol handling | native byte-equivalence fixture와 BedrockProtocol fallback |

Dragonfly와 다르게 유지할 것:

- PHP plugin event는 main thread에서만 실행한다.
- plugin이 관찰 가능한 event 순서는 기존 PMMP를 기준으로 한다.
- worker 결과는 권한이 아니라 후보이며, 최종 적용은 commit phase에서만 한다.

## 400명 동일 구역 hotspot 전략

같은 구역 400명은 region 병렬화만으로는 해결이 안 된다. 전부 같은 region에 있으면 결국 같은 actor에 몰린다. 이 경우 핵심은 `한 tick에 필요한 work 자체를 줄이는 것`이다.

구조:

```text
HotspotController
  detects dense cells
  activates fanout coalescing
  activates packet template cache
  activates cosmetic rate limit
  tracks viewer-set stability

DenseCell
  players bitset
  entities bitset
  lastMovementVersion
  lastVisibleSetVersion
  packetTemplateCache
```

우선순위:

1. movement/rotation packet coalescing
2. viewer set dirty diff
3. shared packet payload
4. chunk payload sharing
5. scoreboard/actionbar/metadata dirty-set
6. cosmetic packet backpressure
7. entity AI/path candidate worker

금지:

- 400명 hotspot에서 모든 player pair를 매 tick 재계산하지 않는다.
- plugin event를 줄이기 위해 event 자체를 건너뛰지 않는다.
- desync를 감수하고 packet을 누락하지 않는다.

## Dragonfly에서 가져올 것과 버릴 것

가져올 것:

- transaction boundary
- handle/proxy 사고방식
- world mutation을 한 경계 안에서 동기화하는 모델
- Go/gophertunnel식 protocol fixture 관리
- library-first 구조의 명확한 internal API

버릴 것:

- PMMP plugin API를 Go API처럼 바꾸는 것
- PHP plugin을 native thread에서 직접 실행하는 것
- 기존 PMMP object identity를 깨는 전면 엔진 교체

## Folia에서 가져올 것과 버릴 것

가져올 것:

- region ownership invariant
- ticking region이 tick 중 ownership 확장 금지
- region-local data
- cross-region task queue

버릴 것:

- 모든 지역을 처음부터 병렬 tick하는 전면 전환
- 플러그인 호환을 깨는 region API 강제
- 400명 hotspot을 region split으로만 해결하려는 접근

## 구현 단계

### Phase 0: 기준선 고정

기간: 1-2일

작업:

- `movement-fanout`, `spawn-chunk-burst`, `hotspot-400`, `plugin-io` scenario 고정

## 예상 성능 목표

Dragonfly = 100 기준 추정:

| 상태 | 목표 |
|---|---:|
| packet/chunk hotpath only | `85-110` |
| release PMMP core, plugin 거의 없음 | `75-95` |
| hotspot worker + chunk snapshot | `70-90` |
| PMMP plugin 호환 많이 유지 | `55-80` |
| 400명 같은 구역 밀집 | `60-85` |
| 넓은 야생 400명, pregen+제한 plugin | `65-90` |

이 수치는 공개 동일조건 벤치가 없으므로 목표치다. 최종 판단은 우리 benchmark artifact로만 한다.

## 실패 조건

다음 중 하나라도 발생하면 해당 lane은 rollback한다.

- PMMP plugin event order 변경
- inventory transaction rollback 오류
- packet byte-equivalence mismatch
- chunk corruption 또는 stale chunk 전송
- worker crash가 main server crash로 전파
- p95 tick이 baseline보다 `10%+` 악화
- memory/player가 `20%+` 증가
- 400명 hotspot에서 disconnect storm 발생

## 바로 할 작업

1. `hotspot-400` benchmark scenario 추가.
2. StandardPacketBroadcaster duplicate serialization counter 추가.
3. movement packet fanout counter 추가.
4. ChunkSnapshot shape를 PHP class로 먼저 정의.
5. native bitset/AOI helper microbench 추가.
6. packet template encode helper를 `pmmp_perf_ext` v2 후보로 구현.
7. PHAR/release bundle 기준으로 benchmark 재실행.

## 최종 판단

가장 좋은 방향은 PMMP를 버리고 새 엔진을 만드는 것이 아니라, PMMP main thread를 compatibility/event commit thread로 축소하고 C/C++ native/worker를 pure data engine으로 확장하는 것이다.

Dragonfly에서 배워야 할 핵심은 Go 자체가 아니라 transaction boundary와 비동기 구조다. Folia에서 배워야 할 핵심은 region ownership invariant와 cross-region queue다. PMMP에서 반드시 지켜야 할 것은 plugin API와 event order다.

따라서 다음 구현 목표는 region actor 전면 전환이 아니라, `hotspot fanout + chunk snapshot + packet/native serialization + dirty-set`을 먼저 끝내는 것이다.
